# 10. 결정 기록 / 확인이 필요한 항목

## 10.1 대화에서 확정한 사실
- 3×3 슬롯머신, 가로·세로·대각선 **8개 페이라인**.
- 매 라운드 목표 점수 달성 실패 시 런 종료.
- 심벌별 등장 가중치 증가와 3일치 배당 증가 아이템을 각각 제공.
- 일부 아이템은 작은 확률로 1칸/라인 결과를 조작; 사용 횟수 또는 Hand 기간 제한.
- `기적의 손`은 후보 라인 **무작위 균등 선택**(최고 배당 선택 아님).
- 코인으로 상점 아이템 구매; 라운드 보상, 미사용 Hand 보너스, 이자 포함.
- **무제한 구매**(코인 한도 내, 인벤토리/상점 재고의 실제 제약은 유지).
- 코인 수치는 낮게 유지. 베팅칩/베팅 규칙은 **잠시 제외**.
- 전체 순위를 보여주는 랭킹 예정.

## 10.2 구현을 위한 현재 추천 가정 (사용자 확정 전)
| 내용 | MVP 제안 | 검증 이유 |
|---|---|---|
| 기본 Hand | **4회** | 요청은 3~4회; 우선 4로 구현 후 비교 |
| 초기 Coin | 0 | 빠른 초기 상점 성장 |
| 클리어 기본 | 2 | 작고 이해 쉬운 화폐 |
| 남은 Hand | +1 coin/Hand | 조기 정산 동기 |
| 이자 | 5코인당 +1, 최대2 | 저축-소비 긴장감 |
| 상점 진열 | 3개 | 선택의 단순성 |
| 리롤 비용 | 유료 1→2→3→… | 무제한 구매의 제어 |
| 영구/제한 슬롯 | 8/2 | 인벤토리 전략; 미확정 |
| 최초 목표 | 120점 | 초기 실패율이 과도하지 않도록 시뮬레이션 기준 |
| 최종 목표 | 10라운드 승리 | 무한 모드 추후 |
| 보드 조작 | 한 Hand에 최대 1개 | 조합 폭주/재현성 관리 |
| 랭킹 | 완료 라운드, 누적점수 순 | 플레이 목표와 경쟁 연결 |

## 10.3 미결정 / Codex가 임의 확정하지 말 것

3. **상점 보유 슬롯 8/2 제한 및 폐기 정책:** 최종 UX 테스트 후 확정.
4. **일일 챌린지/무한 모드:** MVP 이후 도입.
5. **상점 희귀도 출현율·경제 수치:** 플레이 테스트로 조정.
6. **게임 이름:** 브랜딩 후보 중 선택. 상표/서비스 중복 검토 전 가제 사용.
7. **결과 조작 아이템 간 발동 우선순위:** 현 문서의 규칙을 프로토타입 기본값으로 사용하되 추후 조정.
8. **연출 속도/스핀 애니메이션 길이:** 유저 테스트 후 결정.

## 10.5 Phase 0~1 구현 결정 (2026-10-25)
- **저장소 조사:** 기존 프론트/서버/인증/DB/패키지/테스트 프레임워크가 없고 문서, JSON, Python 정적 검사 스크립트만 존재했다. 기존 프레임워크 교체는 없다.
- **실행 기반:** 설치된 Node.js 22, ES modules, 내장 `node:test`를 사용한다. 외부 의존성 없이 순수 도메인 함수와 Node 서버 전용 실행 계층을 분리한다. 프로덕션 프레임워크·DB·로그인 선택은 여전히 보류한다.
- **범위:** Phase 0~1은 아이템 없는 슬롯/라운드 엔진이다. 27종 카탈로그 전체의 구조·참조는 검증하지만 아이템 효과, 코인 지급, 상점, HTTP API, 저장, UI, 랭킹은 다음 단계다. 클라이언트 제공 아이템/보드/점수/코인을 받지 않는다.
- **중간 상태:** 이 단계의 순수 라운드 엔진은 성공을 `ROUND_CLEAR`로 표시한다. 로컬 테스트의 `CONTINUE`는 이 상태에서 다음 라운드로 넘어가며 코인을 지급하지 않는다. 10라운드 성공은 즉시 `RUN_WON`이다. Phase 3 어댑터는 클리어와 보상·상점 진입을 원자 처리해야 하며, 이 테스트용 전환을 실제 상점 건너뛰기 API로 노출하지 않는다.
- **서버 경계:** 메모리 `GameSession`이 서버 생성 시드와 상태를 소유하고 명령의 소유자·revision·Idempotency-Key를 검사한다. `userId`는 향후 인증 미들웨어가 제공할 신뢰된 호출 문맥이며 현재 HTTP 인증 구현은 아니다. 중복 요청 기록과 상태는 프로세스 메모리 범위다. 같은 키+같은 명령은 최초 응답을 반환하고 다른 명령은 거절한다.
- **난수 v1:** `hmac-sha256-counter-v1`. 서버가 32바이트 비밀 시드를 생성한다. 0부터 시작하는 블록 번호에 대해 UTF-8 `nine-to-ruin:rng:v1:<번호>`를 HMAC-SHA256으로 계산하고, 각 블록의 8개 uint32를 big-endian 순서로 소비한다. `[0, bound)` 정수는 rejection sampling으로 추첨한다. 9칸은 행 우선이며 소비 카운터는 버린 uint32도 센다. 비밀 시드·카운터·서버 감사 로그는 공개 응답에서 제외한다.
- **재현:** 서버 감사 기록에 초기 시드, RNG/규칙/라인/카탈로그 버전과 SHA-256 데이터 지문, 승인된 액션, 소비 구간, 보드·점수·revision을 보관한다. 리플레이는 동일한 데이터 지문만 허용하고 모든 이벤트와 최종 상태를 재검산한다. 이 감사 기록의 내보내기는 서버 내부 테스트/저장 통합용이며 클라이언트 API가 아니다.
- **정확한 수치:** 점수는 로딩 시 BigInt로 변환하고 공개 응답은 십진 문자열로 만든다. JSON의 작은 점수 정수도 안전 정수인지 검증하며 큰 값은 문자열만 허용한다. 유리수는 BigInt 분자/분모로 연산한다. 가중치 합은 100으로 고정하지 않되 RNG v1의 정수 범위인 2^32 이하로 검증한다.
- **실패 처리:** Hand 0 미달은 즉시 `RUN_FAILED`; 목표 도달만으로는 남은 Hand를 소모하지 않으며 정산 또는 추가 스핀을 선택한다. 최종 실패 Hand 점수도 누적 점수에 포함한다. 종료된 런은 추가 명령을 거절한다.

## 10.6 Phase 2 구현 결정
- **규칙 v0.5:** 기존 가격/가중치/배당/확률/슬롯 수는 유지한다. `balance.itemRules`에 보드 조작 우선순위, 최고 증가량 동률 처리, 가상 배당 난수 공유, 라운드 간 스트릭 유지 정책을 추가한다. 세 JSON 버전을 함께 올린다. 기존 v0.4 메모리 런/감사 로그는 새 엔진에 암묵적으로 이관하지 않고 버전 불일치로 거절한다.
- **범위:** 22종 전투/점수 효과와 인벤토리 수명/중첩/폐기를 구현한다. 경제 5종은 인벤토리에 보관할 수 있지만 스핀 효과는 없으며 정산/구매 실행은 Phase 3이다. 미지원 효과는 오류로 거절한다.
- **획득:** 같은 영구 아이템도 구매마다 별도 인스턴스를 보관하고 슬롯 사용량만 ID 단위로 센다. 각 인스턴스에 `activeFromRound`를 두어 기존 스택과 다음 라운드부터 적용할 새 스택을 구분한다. 획득 함수는 서버 전용이며 활성 라운드를 반드시 지정한다. Phase 2 데모의 시작 아이템은 서버가 정한 테스트 빌드이고 일반 런 기본값은 빈 인벤토리다. 클라이언트 스핀 명령으로 아이템을 추가할 수 없다.
- **스트릭:** 실제 당첨 라인이 있으면 보유 아이템과 무관하게 연속 Hand 수를 갱신한다. 라운드 성공/정산은 스트릭을 끊지 않고 실제 무당첨 Hand에서만 0으로 만든다. 런 종료 시 인벤토리는 초기화한다.
- **보드 변환:** 후보 순서는 `lines.v0.json` 순서다. 동일 변경 위치/심벌이라도 라인별 후보는 합치지 않는다. 같은 조작 그룹은 획득 순서 → item ID → instance ID 순서로 판정한다. 재추첨을 실행했다면 우연히 같은 심벌이 다시 나와도 발동 성공으로 세며 다른 조작은 실행하지 않는다.
- **계산된 기적:** 모든 라인/전역 배율과 가상 배당까지 반영한 최종 BigInt 점수 차이를 비교한다. 최대 양수 증가량이 동률이면 라인 정의 순서가 앞선 후보를 택하고 추가 난수는 쓰지 않는다. 가상 배당 아이템의 발동 난수는 후보 비교에 처음 필요할 때 한 번만 추첨해 원본·모든 후보·최종 결과에서 공유한다. 후보 미선택/기적 미발동이어도 미리 소비한 난수는 되돌리지 않으며 가상 배당의 실제 발동은 최종 보드의 조건으로 결정한다.
- **난수 순서:** 가중치 적용 후 9칸 → 조건을 만족하는 조작 아이템 순서대로 발동 판정 → 성공한 조작의 후보 선택/열 3칸 추첨 → 최종 가상 배당 판정. 위 최고점 후보 비교의 공유 난수만 필요 시 앞서 예약된다. 조건 미충족은 발동 난수를 쓰지 않고, 확률은 `[0,10000)` 값이 basis points 미만일 때 성공한다. 예약/발동/선택을 서버 감사 로그에 기록한다.
- **수명:** activeFromRound에 도달한 timed는 실제 스핀 종료 후 1 감소(효과 성공 여부 무관), charged는 실제 조작 성공 시만 1 감소한다. 0이 된 인스턴스는 해당 Hand 계산을 마친 후 제거한다. 정산/라운드 전환/중복 요청은 수명을 소모하지 않는다.
- **감사 포맷:** 아이템 초기 상태와 아이템 난수 소비 기록이 추가되어 `slot-audit-v2`를 사용한다. 이전 v1 로그는 명시적으로 거절한다. 시드/난수 원값은 공개 응답에 포함하지 않는다.

## 10.7 Phase 3 구현 결정 (2026-10-26)
- **규칙 v0.6:** 기존 가격·보상·확률은 유지하고 상점 추첨/활성 정책을 JSON에 명시한다. 세 JSON 버전을 함께 올리며 이전 메모리 런을 자동 이관하지 않는다. 경제/상점 명령과 정산 내역을 포함하는 `slot-audit-v3` 로그를 재현하고 구버전 로그는 명시적으로 거절한다.
- **정산 경계:** 목표 달성 후 CLAIM 또는 마지막 Hand 성공에서 보상→상점 진열을 한 액션으로 계산한다. 외부에 노출되는 상태는 바로 `SHOP`이며 `ROUND_CLEAR`는 중간 개념이다. 실패 시 보상/급여일 추첨 없이 코인·인벤토리를 초기화한다. 마지막 라운드도 보상을 계산해 이벤트에 남긴 후 코인·아이템을 초기화하고 `RUN_WON`으로 종료한다. 마지막에는 상품을 추첨하지 않는다.
- **상품 추첨:** 상한에 도달한 item ID를 제외하고, 빈 등급을 제거한 가중치 합으로 등급을 추첨한 뒤 해당 등급 내 상품을 균등 선택한다. 선택한 ID는 같은 진열의 다음 추첨에서 제외한다. 슬롯마다 등급→상품 순으로 난수를 소비하며 후보가 1개여도 각각 1회 추첨한다. 후보 소진 시 나머지는 null인 빈 슬롯으로 남기고 난수를 쓰지 않는다. 리롤에는 직전 상품도 다시 나올 수 있다.
- **진열과 구매 가능성:** 잔액 부족/인벤토리 슬롯 부족만으로 상품을 풀에서 제외하지 않는다. 구매 가능 여부와 거절 이유를 응답에 포함한다. 구매 시에는 최신 코인·최대 스택·슬롯·재고를 다시 검증한다. 구매/폐기는 진열을 자동 보충하지 않는다.
- **구매·폐기:** 구매는 `BUY + slotId`, 폐기는 `DISCARD + instanceId`이고 SHOP에서만 가능하다. 가격/아이템 ID/코인은 클라이언트가 정할 수 없다. 각 구매는 다음 라운드부터 유효한 인스턴스 1개를 추가한다. 폐기는 인스턴스 1개 단위이며 환불 없이 처리한다. 슬롯 ID에는 라운드·진열 세대·위치를 넣어 리롤 이전 슬롯 구매를 거절한다.
- **할인:** 흥정의 달인은 보유 즉시 이후 구매에 적용하고 폐기하면 이후 가격에서 즉시 제외한다. 해당 아이템 자신의 구매에는 소급 할인하지 않는다. 리롤 비용은 할인하지 않는다. 가격 하한은 상점 하한과 할인 효과의 minPrice를 모두 지킨다.
- **VIP:** 새로 산 VIP는 다음 라운드의 성공 후 상점부터 적용한다. 무료 횟수가 남아 있으면 REROLL이 자동으로 무료를 먼저 사용한다. 무료 횟수는 카탈로그 amount에서 읽고 사용 횟수는 상점 상태에 기록한다. 무료 리롤은 유료 카운터를 늘리지 않으며 폐기/재구매로 현재 상점의 사용 기록을 초기화하지 않는다.
- **정수/원자성:** 코인/가격/카운터는 안전 정수로 유지하며 합·곱·나눗셈은 BigInt 중간 연산 후 안전 범위를 검증한다. 초과 시 상태를 바꾸지 않고 거절한다. 현재 원자성/중복 방지는 단일 Node 메모리 세션 범위이며 DB 트랜잭션은 Phase 4다.
- **난수/재현:** 자동 클리어는 슬롯·아이템 추첨→유효 급여일(획득 순서)→상점 진열 순서로 하나의 RNG를 쓴다. 구매/폐기/다음 라운드는 RNG를 쓰지 않는다. 거절/중복 요청은 상태·코인·아이템·난수·로그를 추가 변경하지 않는다.
- **등급 순서:** 등급 구간은 common→rare→epic→legendary 순서로 고정하여 JSON 객체 키 순서가 달라도 동일한 지문/시드의 결과를 유지한다. 실패 보상 0과 경제 아이템의 영구 슬롯 정책은 로더에서도 검증한다.

## 10.8 Phase 4 구현 결정 (2026-10-26)
- **스택/범위:** 기존 Node ESM을 유지하고 내장 HTTP와 `node:sqlite`로 로컬 MVP 서버를 구현한다(Node 22.13 이상, 검증 환경 22.23.2). 프로덕션 DB·웹 프레임워크·로그인 공급자를 최종 선정하는 것은 아니며 기존 서비스 연동 시 어댑터를 교체한다. 게임 수치와 감사 포맷은 v0.6/slot-audit-v3 그대로다.
- **저장:** SQLite WAL, FULL 동기화, 외래 키, BEGIN IMMEDIATE 트랜잭션을 사용한다. 런의 전체 감사 기록(초기 시드·승인 액션·응답·최종 상태)을 암호화해서 저장한다. 요청마다 이를 재검산해 세션과 중복 응답 캐시를 복구하며 공유 DB의 최신 revision에서 명령을 처리한다. 응답은 커밋 후 반환하고 실패 시 런/난수/랭킹을 모두 롤백한다. 현재 전체 로그 재생 방식은 작은 MVP 런을 위한 선택이며 대규모 운영에서는 검증된 스냅샷으로 최적화한다.
- **규칙 고정:** 시작 시 세 JSON 원본을 지문별로 저장한다. 진행 중인 런은 저장된 규칙으로 재생하고 새 런만 현재 배포 규칙을 사용한다. 엔진이 지원하지 않는 과거 정책은 명시적으로 실패하며 임의 변환하지 않는다.
- **시드 보호:** 감사 기록은 AES-256-GCM으로 암호화하고 runId/소유자/규칙 지문을 인증 데이터에 포함한다. 키는 DB 밖의 권한 제한 파일로 보관한다. 런타임 디렉터리는 0700, DB/키는 0600이며 HTTP는 파일/키/감사 로그를 제공하지 않는다. 키 분실·불일치·기록 변조는 복구를 거절한다. DB와 키를 함께 백업해야 한다.
- **인증:** 기존 계정 서비스가 없어 운영자 CLI에서 계정 식별자에 대한 256비트 불투명 Bearer 토큰을 발급하고 DB에는 SHA-256 해시만 저장한다. HTTP는 사용자 ID/시드/초기 빌드 입력을 받지 않는다. 게스트 가입/비밀번호/외부 로그인은 추가하지 않는다. 계정별 토큰 폐기가 가능하고 API 인증 함수는 외부 로그인 어댑터로 교체 가능하다. 기본 바인딩은 127.0.0.1이며 외부 서비스 배포의 HTTPS·로그인은 별도 연동한다.
- **복구/요청:** 런 생성도 Idempotency-Key로 중복 방지한다. 액션은 키와 expectedRevision을 요구하고 원래 응답을 재시작 후에도 반환한다. GET 내 런 목록/상태/마지막 액션·스핀으로 재접속한다. 앱 종료는 포기가 아니며 진행 상태를 유지한다. 본문 크기/시간 제한과 프로세스별 요청 빈도 제한을 둔다.
- **랭킹:** 종료된 서버 런만 같은 트랜잭션에서 자동 반영한다. 계정당 최고 기록 1개, 완료 라운드 내림차순→정확한 십진 점수 내림차순→서버 종료 시각 오름차순이다. 세 값이 완전히 같은 서로 다른 계정은 runId 순으로 안정 정렬한다. 시각은 서버가 생성하며 중복 요청으로 변경하지 않는다. MVP 일반 랭킹은 저장된 규칙 버전 전체를 포함하고 버전을 표시한다. 외부에는 내부 계정 ID 대신 키 기반 불투명 playerId를 반환한다. 점수 제출 API는 없다.
- **한계:** 동일 호스트의 여러 프로세스가 같은 SQLite 파일을 공유하는 범위다. 네트워크 파일시스템·분산 DB·자동 키 교체·운영 로그인·브라우저 UI는 이 단계 범위가 아니다.
